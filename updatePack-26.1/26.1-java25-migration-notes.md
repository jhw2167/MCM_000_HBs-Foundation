# Migration Notes: Java 25 / Gradle 9 / Minecraft 26.1

Reference for updating other modules and future projects. Captures the IDE
and toolchain changes made at the project level, plus the specific Fabric and
NeoForge `build.gradle` edits that got a 26.1 multiloader project building on
Java 25.

## Why this migration happens together

Java 25, Gradle 9, IntelliJ 2025.3, and Minecraft 26.1 are a coupled set. You
cannot adopt one without the others:

- Minecraft 26.1 is the first **unobfuscated** version and targets **Java 25**.
- Java 25 as the Gradle daemon JVM requires **Gradle 9.1.0+** (8.x cannot run on
  Java 25 at all — fails with `Unsupported class file major version 69`).
- Full Java 25 support in IntelliJ requires **2025.3+**. Older builds reject all
  JDK 25 installs as "corrupt" (their `JavaVersion.parse()` can't parse the 25.x
  version string), regardless of vendor.

## IDE-level changes (IntelliJ)

- **Upgrade IntelliJ to 2025.3 or newer.** Pre-2025.2 builds cannot parse Java 25
  version strings and report every JDK 25 install (Oracle, Adoptium, Microsoft,
  Loom) as corrupt. No cache invalidation or reinstall of the JDK fixes this —
  only the IDE upgrade does.
- **Install a JDK 25** from any major vendor. Any vendor works once the IDE is
  current; the "corrupt" rejection was an IDE parser bug, not a bad download.
- **Register the JDK 25 SDK** in Project Structure with a known name. The Gradle
  JVM setting references the SDK **by name** — see the gradle.xml note below.

## Project-level Gradle changes

### Gradle wrapper -> 9.1.0+ (9.3.0 used here)

In `gradle/wrapper/gradle-wrapper.properties`:

```properties
distributionUrl=https\://services.gradle.org/distributions/gradle-9.3.0-bin.zip
```

Or regenerate the wrapper (also refreshes the wrapper jar/scripts):

```bash
./gradlew wrapper --gradle-version=9.3.0
./gradlew wrapper
```

### `.idea/gradle.xml`

      <option name="externalProjectPath" value="$PROJECT_DIR$" />
<option name="distributionType" value="DEFAULT_WRAPPED" />
<option name="gradleJvm" value="25" />

### Loader plugin minimum versions for 26.1 / Gradle 9

- **Fabric Loom**: 1.15+ (1.14.x does not support 26.1). Supports Gradle 8.14 / 9.0;
  verify on 9.1+.
- **NeoForge ModDevGradle**: 2.0.134+ for the 26.1 snapshots.
- Confirm where the loader plugin **version** is pinned — often `settings.gradle`
  `pluginManagement`, or a convention plugin in `buildSrc` (e.g. a
  `multiloader-loader` plugin). Bump it there, but be careful not to drag
  still-obfuscated targets onto the wrong plugin.

## Fabric `build.gradle` changes (26.1 = unobfuscated)

The single biggest concept: **26.1 is unobfuscated, so nothing is remapped.**
That drives every change below. Symptoms if you miss it:

- `Failed to find official mojang mappings for <version>`
- `Could not resolve net.fabricmc:intermediary:<version>` /
  `inconsistent module metadata ... expected='<ver>' found='0.0.0'`

Both mean the remapping plugin is still active on a version that must not be
remapped.

### 1. Plugin ID: remapping -> non-remapping

```diff
 plugins {
     id 'multiloader-loader'
-    id 'fabric-loom'
+    id 'net.fabricmc.fabric-loom'
 }
```

Plugin ID reference (choose by whether the target is obfuscated):

| Plugin ID                          | Use for                                   |
|------------------------------------|-------------------------------------------|
| `net.fabricmc.fabric-loom`         | Unobfuscated versions (26.1+)             |
| `net.fabricmc.fabric-loom-remap`   | Obfuscated versions (1.21.11 and older)   |
| `fabric-loom` (legacy)             | Backwards compat only — use `-remap`      |

The non-remap plugin does not resolve `intermediary` at all, which is what clears
the metadata error.

### 2. Remove the `mappings` block entirely

```diff
-    mappings loom.layered {
-        parchment("org.parchmentmc.data:parchment-${parchment_minecraft}:${parchment_version}@zip")
-    }
```

No remap step exists for unobfuscated Minecraft, so there are no mappings to
apply. Parchment (a mappings layer) goes with it. 26.1 source uses Mojang's
official names directly.

### 3. `modImplementation` -> `implementation` (and related)

```diff
-    modImplementation "net.fabricmc:fabric-loader:${fabric_loader_version}"
-    modImplementation "net.fabricmc.fabric-api:fabric-api:${fabric_version}"
-    modImplementation("net.blay09.mods:balm-fabric:${balm_version}") {
+    implementation "net.fabricmc:fabric-loader:${fabric_loader_version}"
+    implementation "net.fabricmc.fabric-api:fabric-api:${fabric_version}"
+    implementation("net.blay09.mods:balm-fabric:${balm_version}") {
         transitive = false
     }
```

The `mod`-prefixed configurations only exist to feed the remap step. With nothing
remapped, use standard configurations:

- `modImplementation` -> `implementation`
- `modCompileOnly` -> `compileOnly`
- `remapJar` -> `jar`

### Unchanged in the Fabric file

The `loom { accessWidener, mixin, runs { client / server } }` block needs no
changes for this migration. `jsr305` was already a plain `implementation`.

## NeoForge `build.gradle` changes (for cross-reference)

NeoForge needed less work — the plugin (`net.neoforged.moddev`) was already
correct. Two edits:

### 1. Parchment: block form -> single artifact coordinate

```diff
-    parchment {
-        minecraftVersion = parchment_minecraft
-        mappingsVersion = parchment_version
-    }
+    parchment.parchmentArtifact = "org.parchmentmc.data:parchment-${parchment_minecraft}:${parchment_version}@zip"
```

If Parchment has not published for the 26.1 snapshot yet, delete the line
entirely — Parchment is optional (parameter names only); 26.1 uses official
Mojang names regardless.

### 2. Datagen run type: `data()` -> `clientData()`

The `data` run type was split into `clientData` and `serverData`. Symptom:

```
Trying to prepare unknown run: data.
Available run types: [client, clientData, serverData, gameTestServer, server, junit]
```

Fix — keep the block **named** `data` (so the `runData` task name is unchanged),
change only the type call:

```diff
         data {
-            data()
+            clientData()
             programArguments.addAll '--mod', project.mod_id, '--all', '--output', ...
         }
```

NeoForged recommends generating all assets and data in a single `clientData` run
rather than splitting into `clientData` + `serverData` (splitting produces two
output folders that then need reconciling).

## Quick migration checklist

1. IntelliJ -> 2025.3+
2. Install + register JDK 25; set `.idea/gradle.xml` `gradleJvm` to the SDK's
   exact name
3. Gradle wrapper -> 9.1.0+ (`gradle-wrapper.properties` or `./gradlew wrapper`)
4. Bump loader plugin versions (Loom 1.15+, ModDevGradle 2.0.134+) wherever
   they're pinned
5. Fabric: swap to `net.fabricmc.fabric-loom`, delete `mappings`, `modImplementation` -> `implementation`
6. NeoForge: Parchment -> `parchmentArtifact` coordinate (or remove); `data()` -> `clientData()`
7. Keep older-MC (1.20.1 / 1.21.1) modules on the remap plugin + their own
   Java 17/21 toolchain — do not let them inherit 25 or the non-remap plugin
